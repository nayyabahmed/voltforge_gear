# REF-001 — Recommendation Report: Publishing the Handbook as an Interactive Edition

**Date:** 2026-08-06
**Prepared for:** VoltForge Gear — The Young Engineer's Handbook
**Question:** How do we turn 44 Markdown topics into something as accessible
and interactive as *How to Think Like a Computer Scientist* or *Think Python*,
once the topics are written and reviewed?
**Status:** Recommendation for decision. No work started.

---

## Executive Summary

**Recommended: Quarto as the publishing platform, with interactivity added in
three cheap layers on top of conventions the book already has.**

The two reference projects are both *programming* books, and almost all of
their interactivity is one feature — run code in the browser and get instant
feedback. This handbook has no code to run. Copying their toolchain would
import a large amount of machinery to power the one capability that does not
apply to us.

What does transfer is the *shape* of what they offer: a free web edition that
sits alongside the paid book, self-checking questions, and saved progress.
All three are achievable here without adopting their stack.

Two findings should shape the decision more than the tool comparison does:

1. **The real blocker is not the toolchain — it is the 76 unrendered sketch
   placeholders.** Every platform below renders images equally well. None of
   them will draw the pictures. An interactive edition built on placeholder
   text will be worse than the current PDF, however good the platform.
2. **The most valuable interactive feature for this project is progress
   tracking, not quizzes** — because the handbook is the spine of a paid
   programme with kits and weekly sessions starting 27 July 2026. Knowing which
   topics a child has finished is worth more than a drag-and-drop puzzle.

Recommended sequence: do nothing to the toolchain now, spend the interval
commissioning illustrations, then migrate to Quarto in one step after the
review passes finish.

## 1. What the reference projects actually do

| | *How to Think Like a Computer Scientist* | *Think Python* (3rd ed.) |
| --- | --- | --- |
| Platform | Runestone Academy | Jupyter Book + GitHub Pages |
| Authoring source | PreTeXt (XML) | Jupyter notebooks (`.ipynb`) |
| Core interactivity | In-browser Python (Skulpt), Parsons drag-and-drop puzzles, multiple-choice with instant feedback, saved progress | Every chapter is a runnable notebook; "Open in Colab" on each chapter |
| Why it works | The subject *is* the interactive element — code you can edit and run | Same |
| Business model | Free, non-profit, NSF-supported consortium | Free web edition, paid O'Reilly print edition |

**The critical detail.** Runestone's saved progress and instructor dashboards
require the **Runestone server**. If you self-host the generated static HTML,
questions still grade themselves and give instant feedback, but *responses and
scores are not saved anywhere*. The feature most worth having is the one that
needs infrastructure.

**What this means for us.** Their interactivity is inseparable from their
subject. Ours is not: a child cannot "run" a soldered joint or a printed
bracket in a browser. Our equivalent of "run the code" is *go and build it,
then come back* — which is exactly what the Topic Mini Projects already do.
The web edition's job is to support that loop, not to replace it.

## 2. Criteria, derived from this project

Weighted by what this handbook actually is, not by what is fashionable.

| # | Criterion | Why it matters here | Weight |
| --- | --- | --- | --- |
| 1 | Image-heavy rendering | 76 illustration slots pending; the book teaches physical, spatial skills | High |
| 2 | Keeps PDF + EPUB | `build_book.py` already produces a print-ready PDF with full-page covers; the programme likely ships a printed book | High |
| 3 | Low authoring migration | 30 files, 37,705 lines of GitHub-flavoured Markdown, plus all the conventions in STYLE-GUIDE.md | High |
| 4 | Mermaid support | 73 mermaid blocks across the book | High |
| 5 | Prominent, consistent callouts | Safety content is the strictest thing in the book; `⚠️ SAFETY` must be unmissable | High |
| 6 | Reader progress tracking | Topic Checklists exist in every topic; the programme has cohorts and weekly sessions | Medium-High |
| 7 | Search across the whole book | 44 topics and a 428-entry glossary | Medium |
| 8 | Self-check questions | Every topic already ends with 8–12 Review Questions | Medium |
| 9 | Works on a phone at the bench | The reader is building at a table, not sitting at a desk | Medium |
| 10 | No code execution needed | We have none | — |

Criterion 10 is why the reference stacks score poorly: their headline feature
is worth nothing to us.

## 3. Options

### A. Quarto — **recommended**

A scientific and technical publishing system built on Pandoc.

- **Migration cost: low.** It is Pandoc underneath, which is what
  `build_book.py` already shells out to. Existing `.md` files are usable;
  `SUMMARY.md` maps onto Quarto's book chapter list.
- Native Mermaid across every format — rendered live in HTML, and
  auto-converted to PNG via Chrome for PDF and EPUB. This is precisely the
  workaround `build_book.py` implements by hand with `mmdc` today, so that
  custom code can be retired.
- One source → website + PDF + EPUB. Directly replaces the current pipeline
  rather than sitting beside it.
- Built-in callout blocks (note/warning/caution/tip) that the emoji callout
  markers map onto cleanly.
- Cross-references, numbered figures, and client-side search included.
- **Weakness:** no accounts or saved progress. Layer 2 below covers this.
- **Weakness:** the website is good but not as polished as Material for
  MkDocs.

### B. MyST / Jupyter Book 2

The *Think Python* lineage, substantially rewritten.

- Jupyter Book 2 is a complete rewrite on the **MyST document engine**
  (JavaScript/TypeScript), not Sphinx. Faster builds, modern web output.
- Important: the **Sphinx-based stack is now in maintenance mode** while the
  core team focuses on MyST. Choosing Sphinx today (the third Gemini
  suggestion) means choosing the maintenance-mode path.
- MyST Markdown is a CommonMark superset, so migration is moderate.
- **Weakness:** its differentiator is executable notebooks and scientific
  cross-referencing. We would carry the weight and use little of it.
- A reasonable second choice, and the natural pick *if* Part 5 ever grows
  computational content (telemetry plots, data logging from Topic 5.2).

### C. Runestone + PreTeXt

The *How to Think Like a Computer Scientist* stack.

- **Migration cost: severe.** PreTeXt is XML. This means converting 37,705
  lines of Markdown into a different authoring language, and rewriting
  STYLE-GUIDE.md around it.
- Saved progress needs the Runestone server run and maintained.
- Designed around CS and mathematics; our content is neither.
- **Verdict: reject.** The cost is enormous and the payoff — in-browser code
  execution — is the one thing we cannot use. Its genuinely useful parts
  (multiple choice, Parsons problems, progress) are obtainable far more
  cheaply.

### D. Material for MkDocs

- The best *website* of the group: excellent navigation, superb instant
  search, first-class Mermaid, and admonitions that map directly onto the
  callout markers.
- Very low migration cost — it consumes plain Markdown.
- **Weakness:** website-first. PDF export is a second-class plugin and there
  is no real EPUB path. We would keep `build_book.py` for print and run two
  pipelines.
- **Choose this instead of Quarto if** the website is the primary deliverable
  and print becomes secondary.

### E. mdBook / Honkit

- Already noted as an option in `BUILD.md`. Honkit reads a `SUMMARY.md` in
  exactly the format this repo already maintains, so a browsable site is close
  to free.
- **Weakness:** low ceiling — limited interactivity, weaker search, no
  multi-format story.
- **Good as a stopgap**, not as the destination. Worth 30 minutes if you want
  a public web edition before the review passes are finished.

### F. Docusaurus

- Strong versioning and translation support, React-based.
- Overkill unless the handbook needs multiple language editions or many
  simultaneous published versions. Revisit only if the programme
  internationalises.

## 4. The interactivity layers

Platform choice and interactivity are largely independent. The book's existing
conventions are already the right raw material — this is the most encouraging
finding in this report.

### Layer 1 — free, from structure the book already has

| Existing convention | Becomes |
| --- | --- |
| `# Topic Checklist ✅` with `- [ ]` items | Tickable boxes, saved in the browser, feeding a per-topic progress bar |
| `# Review Questions ❓` | Click-to-reveal model answers |
| `# New Words 📖` + 428-entry `glossary.md` | Hover/tap tooltips on first use, auto-linked |
| `> **🤔 Think about it.**` | Collapsed by default, so the reader genuinely pauses before the answer |
| `> **⚠️ SAFETY**` | Styled callout that cannot be skimmed past |
| `> **🎬 Watch the build**` | Embedded thumbnails instead of bare links |

All of this is CSS and a small amount of JavaScript over the generated HTML.
No accounts, no backend, no per-reader data leaving the device.

### Layer 2 — progress that survives, still no backend

Persist checklist state to `localStorage` and add a "your progress" page
driven by `SUMMARY.md`. For a child working through 44 topics over months,
this is the single highest-value feature in this report, and it costs a
few hundred lines of JavaScript.

### Layer 3 — only if the programme needs it

For cohorts, parent/mentor visibility, or certificates, progress must sync to
an account. Options, cheapest first:

- **H5P** — open-source, 50+ interactive content types (multiple choice,
  drag-and-drop, branching scenarios, interactive video), embeddable, and the
  de-facto standard for interactive educational content. Authoring is
  GUI-based, so content lives outside the Markdown — a real drawback for a
  single-source book. Lumi can export standalone HTML if no server is wanted.
- **A small custom backend** — accounts plus a progress table. More control,
  more obligation: this is children's data, so it brings UK GDPR duties,
  parental consent, and a retention policy with it.

**Recommendation: do not build Layer 3 until the programme proves it needs
it.** Layers 1 and 2 deliver most of the felt interactivity at a fraction of
the cost and with no personal data at all.

## 5. Recommendation and phasing

**Phase 0 — now, before any platform work (highest value).**
Commission or draw the 76 illustrations. This is the real bottleneck, it is
entirely platform-independent, and it can proceed in parallel with the Part 2
and Part 3 review passes. A beautiful platform showing
`**[Sketch: ...]**` placeholders is worse than today's PDF.

**Phase 1 — while reviews continue: protect optionality.**
Keep `SUMMARY.md` as the single source of order and status; it is what makes
every option above cheap. Avoid platform-specific Markdown extensions in
topic prose. Optionally stand up Honkit for a quick public web edition, on the
explicit understanding that it is a stopgap.

**Phase 2 — after Part 2 and Part 3 reach v0.2: migrate to Quarto.**
One `_quarto.yml` generated from `SUMMARY.md`; retire the hand-rolled Mermaid
pre-render in `build_book.py` in favour of Quarto's; port `print.css`; verify
the full-page cover behaviour survives, since that is the most bespoke part of
the current PDF and the most likely thing to break.

**Phase 3 — with the first real cohort: add Layers 1 and 2.**
Ship the styled callouts, glossary tooltips, revealed answers and saved
checklist progress together, and watch what the cohort actually uses.

**Phase 4 — only on evidence: Layer 3 accounts.**

## 6. Risks

| Risk | Severity | Mitigation |
| --- | --- | --- |
| The PDF regresses during migration — covers, page breaks, emoji fonts are all bespoke today | High | Keep `build_book.py` working until the Quarto PDF is compared side by side against a known-good build. Do not delete it on day one. |
| Interactive edition ships with placeholder art | High | Phase 0 first. Treat illustration count as the release gate, not topic count. |
| Effort diverted from writing | Medium | Nothing here is on the critical path before the reviews finish. Phase 0 is the only concurrent activity, and it is not authoring work. |
| Children's data obligations arrive with accounts | Medium | Layers 1–2 store nothing off-device. Defer Layer 3 until there is a clear need and a consent process. |
| Two pipelines drift if MkDocs is chosen for web and `build_book.py` kept for print | Medium | Prefer the single-source option (Quarto) unless the website is judged more important than print. |
| Platform abandonment | Low | Quarto is Pandoc-based, so the source stays portable Markdown; the exit cost stays low by construction. |

## 7. Decision: HTML is an output, not a source

**Question raised 2026-08-06:** if the goal is interactive HTML, should the
topics be authored in HTML rather than Markdown?

**Decision: no. Markdown stays the source; HTML is a build output.**

The phrase "shift to HTML" conflates two separate things. As an *output*,
HTML is the entire point of this report — figure grids, side-by-side panels,
saved checklist progress, glossary tooltips, collapsible prompts and search
are all rendering features, and Quarto produces them from the Markdown that
already exists. As a *source* format it would be a substantial net loss.

**What depends on Markdown structure today:**

| Construct | Count | Depends on it |
| --- | ---: | --- |
| ATX headings | 2,461 | `build_book.py` splits topics on `^# `; `SUMMARY.md` parsed on `^## ` |
| Pipe table rows | 1,308 | New Words, comparisons, decision matrices |
| `- [ ]` checklist items | 412 | Topic Checklists — the Layer 2 progress feature reads these |
| Blockquote callouts | 245 | The fixed `⚠️ 🤔 📚 🎬 ☕` marker registry |
| `### Term` glossary entries | 428 | Alphabetical ordering and coverage checks |

**Three reasons the source stays Markdown:**

1. **It would break the review workflow, which is the current critical path.**
   Part 2 has eight topics left and Part 3 has ten, all driven by readable git
   diffs — which is also how author annotations are found. HTML diffs are far
   noisier. This would degrade the process actively in use to gain nothing the
   output layer does not already provide.
2. **It would break the tooling.** `build_book.py` matches headings, `.md`
   links and mermaid fences. So do the audit scripts that produced the glossary
   coverage checks and the figure-density measurements in REF-002.
3. **It would cost the free preview.** GitHub renders both the Markdown and
   the Mermaid natively, which is what makes the book readable today.

**The nuance.** Markdown permits inline HTML, and both Pandoc and Quarto pass
it through. Where a layout genuinely needs it — the F3 right-versus-wrong
pairs and F7 comparison arrays of REF-002 — drop into HTML at that one spot,
ideally wrapped in a Quarto shortcode so topics stay readable. Note also that
the format which unlocks the figure programme is **SVG, not HTML**: labels stay
selectable and correctable, it scales to print, it survives greyscale, and it
can be made theme-aware later. An `.svg` is referenced *from* Markdown, so no
migration is involved.

**Consequence for authoring.** Because HTML is the target, Markdown must be
written so a build step can reliably turn it into components. That is a
style-guide matter, addressed in STYLE-GUIDE.md section 13 ("Authoring for
Three Outputs"), added 2026-08-06 as a direct consequence of this decision.

## 8. Answering the Gemini suggestions directly

| Suggestion | Assessment |
| --- | --- |
| **Runestone / Skulpt** for gamified coding puzzles | Reject. Its value is in-browser code execution and Parsons problems for *code*; we have no code. Migration to PreTeXt XML is a rewrite of the whole book, and saved progress needs their server. |
| **Jupyter Book** for visual experiments and labs | Viable, and the closest thing to a "second choice" — but note it now means Jupyter Book **2 on the MyST engine**, not the Sphinx-based version most tutorials describe. Its notebook strength is unused here. |
| **Sphinx** for traditional print/e-book | Do not start here in 2026: the Executable Books Sphinx stack is in maintenance mode, and Pandoc (already in use, and what Quarto wraps) is a better fit for print output. |

The suggestions are sound for a *programming* book. The mismatch is the
subject matter, not the reasoning.
